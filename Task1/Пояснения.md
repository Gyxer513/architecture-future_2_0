# C4. Контейнерная диаграмма целевой архитектуры (T+12 месяцев)

## Акторы

- **Оператор клиники**  
  Работает в медицинских операционных системах (EHR/HIS). Не делает аналитику.

- **Операции финтех**  
  Работают с OLTP, транзакциями, операционными отчётами.

- **Бизнес-аналитик / менеджмент**  
  Self-service отчёты, контроль KPI, ad-hoc вопросы.

- **Дата-инженер / аналитик**  
  Пайплайны, витрины, пайплайны качества, lineage.

- **Дата-саентист (ИИ)**  
  Обучает / деплоит модели на мед. данных в защищённой зоне.

- **Офицер по комплаенсу / ИБ**  
  Политики доступа, аудит, ИУР (регуляторы).

## Верхнеуровневые системы

- **Облачная платформа данных «Будущее 2.0»**  
  Единая среда для доменов.

- **Клинические системы (EHR/HIS, PACS/VNA)**  
  Операционный контур.

- **Финтех-микросервисы**  
  Операционный контур домена банка.

- **Легаси DWH SQL Server (read-only, переходный период)**

# Контейнеры внутри облачной платформы данных

## 1. Ingest / интеграция

- **CDC-интеграция**  
  **Назначение:** Потоковая репликация изменений из OLTP (финтех, внутренние системы, частично — медконтур для служебных атрибутов).  
  **Технологии:** Debezium / Fivetran / GoldenGate.  
  **Выход:** Пишет в шину событий и слой Bronze.

- **Шина событий**  
  **Назначение:** Доменные события и командные топики (event-driven интеграция между доменами и данными).  
  **Технологии:** Kafka / Pulsar.

- **ESB / адаптеры**  
  **Назначение:** Мост к легаси- и внешним системам, где нет событийной архитектуры.  
  **Технологии:** Apache Camel.  
  **Выход:** Выдаёт данные в Kafka или ingest API.

---

## 2. Хранилище и обработка (Lakehouse)

- **Enterprise Data Lakehouse**  
  **Назначение:** Единый слой хранения с медальонной архитектурой.  
  **Слои:**
    - **Bronze** — сырые данные (encrypted at rest).
    - **Silver** — очищенные / нормализованные.
    - **Gold** — тематические Data Marts (бизнес-витрины).  
      **Технологии:** Object Storage (S3 / Blob / GCS) + Delta / Iceberg / Hudi.

- **Batch / Stream Processing**  
  **Назначение:** Трансформации, инкрементальные витрины, проверки качества данных (DQ).  
  **Технологии:** Spark / Flink / Kafka Streams.

- **Оркестрация пайплайнов**  
  **Назначение:** Управление расписаниями, зависимостями, ретраями, CI/CD для данных.  
  **Технологии:** Airflow / Argo / Prefect.

# 3. Доступ и потребление

- **Портал самообслуживания («витрина данных»)**  
  **Назначение:** «Магазин» витрин и метрик, поиск по каталогу, конструктор отчётов, запрос датасетов on-demand.  
  **Интеграции:** Каталог, Семантический слой, BI-система.

- **BI-система**  
  **Назначение:** Дашборды и стандартная отчётность с поддержкой RLS (row-level security).  
  **Технологии:** Power BI / Looker / QuickSight.

- **API Gateway / Service Mesh**  
  **Назначение:** Публикация данных, метрик и фич через API; предоставление доступа к ML-сервисам.  
  **Технологии:** Kong / Apigee + Istio / Linkerd.

- **Каталог и lineage**  
  **Назначение:** Сквозная видимость данных: владельцы, SLA, классификация PII/PHI, data contracts, отслеживание происхождения (lineage).  
  **Технологии:** DataHub / OpenMetadata / Apache Atlas.

- **Доступ / IAM и политики**  
  **Назначение:** Управление доступом через ABAC / RBAC, динамическое маскирование, токенизация, интеграция с KMS, аудит действий.  
  **Интеграция:** С корпоративным Identity Provider (IdP).

---

# 4. Secure-зона для медицинских данных (PHI/PII)

- **Медицинское хранилище**  
  **Назначение:** Хранение медицинских карт, историй болезни, изображений (PACS/VNA).  
  **Особенности:** Полностью изолировано; данные не включаются в аналитические витрины без согласования.

- **ML-платформа**  
  **Назначение:** Обучение и инференс моделей на деперсонализованных или явно согласованных данных.  
  **Компоненты:** MLflow / Feature Store / Model Registry.  
  **Политика вывода:** Только агрегированные или деперсонализованные фичи могут экспортироваться в Lakehouse (в соответствии с политикой DLP).

- **ИИ-сервисы**  
  **Назначение:** Продуктивный inference моделей (например, поддержка врача при диагностике).  
  **Особенности:** Доступ строго регламентирован и подлежит аудиту.

# 5. Операционные домены (вне платформы)

- **Финтех-микросервисы**  
  **Назначение:** Счета, транзакции, кредиты, риск.  
  **Интеграция:** Публикуют события в шину событий, читают агрегаты через API или Gold-витрины.

- **Легаси DWH SQL Server**  
  **Роль:** Временный read-only источник и референтная точка для проверки корректности данных во время миграции.

# Как архитектура поддерживает ключевые сценарии

## Быстрая отчётность и self-service

- **CDC + Streaming → инкрементальные пайплайны до Silver/Gold**  
  SLA по витринам — минуты/десятки минут, а не часы.
- **Семантический слой**  
  Единые определения KPI, минимизация «Excel-логики»; поддержка RLS/ABAC для безопасного self-service.
- **Портал самообслуживания**  
  Поиск датасетов, заявка на доступ, конструктор отчётов поверх семантической модели; каталог витрин с указанием владельцев и SLA.
- **DQ-гейты**  
  Автоматические проверки качества данных блокируют публикацию при нарушениях → меньше ручных сверок, выше доверие к данным.

## Независимое развитие финтех и ИИ

- **Разделение доменов + event-driven контракты (шина событий)**  
  Каждый домен управляет своими пайплайнами и вычислительными кластерами.
- **Secure PHI-зона**  
  Медкарты и изображения полностью изолированы; в Lakehouse выносятся только агрегированные или деперсонализованные фичи в соответствии с политикой DLP.
- **ML-платформа и Feature Store**  
  Независимый жизненный цикл моделей; публикация inference и фич через API Gateway.

## Масштабирование под новые бизнесы

- **Шаблоны data-продуктов**  
  Стандартизированный путь: ingest → bronze → silver → gold с встроенными DQ, каталогом и контролем доступа. Онбординг новых доменов — за недели.
- **Облачная эластичность**  
  Динамическое масштабирование кластеров под нагрузку: BI / ad-hoc-запросы vs тяжёлые батчи; изоляция ресурсов по проектам или аккаунтам.

## Надёжность / комплаенс

- **Geo-репликация + резервное копирование**  
  Lakehouse и метаданные защищены; отработаны DR-планы.
- **Политики доступа**  
  ABAC, динамическое маскирование и токенизация PII/PHI; полный аудит действий в каталоге.
- **Сетевая сегрегация**  
  Чёткое разделение периметров: медицинская Secure-зона и общая аналитическая зона.

# Проблемные места и влияние на сценарии

## Текущее / переходное состояние

| Проблема | Влияние |
|--------|--------|
| **Монолитный SQL Server DWH** | Часовые регенерации витрин → медленные управленческие решения, высокий TCO, узкое место для onboarding новых доменов. |
| **Тяжёлые ETL и пакетная интеграция через ESB** | Высокая латентность → «вчерашние» отчёты; риск для финтех-операций и риск-менеджмента. |
| **Смешение логики и хранилища в DWH** | Любое изменение логики требует длительных релизов; высокая связанность (coupling) всех отчётов. |
| **Отсутствие единого семантического слоя и каталога** | Расхождение в метриках, необходимость ручных согласований, потеря доверия к данным. |
| **Неполная сегрегация PHI/PII** | Регуляторные риски, ограничения доступа, невозможность реализовать полноценный self-service. |
| **Отсутствие централизованного контроля качества и SLA** | Сбои в отчётности, ручные исправления, замедление time-to-insight. |
| **Ограниченная масштабируемость on-prem** | Конкуренция за ресурсы между BI, data science и витринами → снижение производительности и гибкости. |

# Приоритизация (MoSCoW) с привязкой к целям

## Must have — критично для выручки, Time-to-Market (TTM) и комплаенса

- **Базовая платформа Lakehouse**  
  Object Storage + Delta/Iceberg/Hudi; изоляция по доменам (ресурсная и логическая).

- **Потоковая загрузка (CDC + Kafka)**  
  Для ключевых доменов: финансы, клиенты, счета, транзакции.

- **Управление данными и безопасность**  
  Каталог + lineage, IAM/ABAC, полный аудит, DLP/маскировка, строго сегрегированная PHI-зона.

- **Оркестрация и качество данных**  
  CI/CD для data-пайплайнов, единый контроль качества (DQ-гейты на этапе публикации).

- **Семантический слой и ядро Gold-витрин**  
  Витрины: Финансы, Продажи, Клиенты, Риски; поддержка RLS.

- **Портал самообслуживания (MLP)**  
  Поиск датасетов, карточки с метаданными, заявка на доступ, прямой переход в BI-инструмент.

- **Надёжность и наблюдаемость**  
  DR-планы, резервное копирование Lakehouse и метаданных, мониторинг платформы (SLI/SLO).

---

## Should have — ускоряет TTM и независимость доменов

- **ML-платформа и Feature Store**  
  Возможность публикации агрегированных / деперсонализованных фич из secure-зоны в аналитический слой.

- **API Gateway**  
  Выдача метрик, витрин и фич внешним потребителям, включая финтех-микросервисы.

- **Эволюция интеграций**  
  Рефакторинг ESB → событийная модель для новых доменов; для легаси — адаптеры «ESB → Kafka».

- **Кэширование и материализация**  
  Для топ-дашбордов с требованием латентности ≤1 минуты.

---

## Could have — улучшения качества, UX и стоимости

- **Реалтайм-дашборды**  
  Для критичных KPI: операционные риски, антифрод, мониторинг транзакций.

- **Cost governance**  
  Автомасштабирование, квоты и лимиты на ad-hoc-запросы, оптимизация партиционирования и форматов хранения.

- **Маркетплейс data-продуктов в портале**  
  Шаблоны онбординга новых доменов, SLA, скоры качества данных, рейтинги.

---

## Won’t have (в этом году)

- **Полная ликвидация SQL Server DWH**  
  Остаётся в режиме read-only на 6–12 месяцев для «двойной записи» и сверок в переходный период.

- **Включение медицинских карт / изображений в общие витрины**  
  Только агрегированные или полностью деперсонализованные данные, прошедшие DLP-контроль.
